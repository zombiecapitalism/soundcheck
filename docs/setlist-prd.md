# PRD — 내한공연 셋리스트 예측 & 예습 서비스 (Soundcheck)

- 작성일: 2026-07-29
- 개정일: 2026-07-30
- 버전: v0.2 (확장 기능 반영)
- 상태: MVP + 확장 기능(E1~E11) 구현 완료 (2026-07-31, 구현 순서는 `/docs/implementation-plan.md`)

---

## 1. 개요

내한이 확정된 락 밴드의 최근 투어 셋리스트 데이터를 분석해 **"이번 공연에서 어떤 곡을 연주할 확률이 높은지"** 를 예측하고, 각 곡에 대해 **RAG 기반 배경 설명**(곡의 의미, 라이브 특징, 명연 버전)을 제공하는 공연 예습 서비스.

### 목적

- 1차: 실사용자가 존재하는 완성도 높은 포트폴리오 프로젝트 (수익성은 필수 조건 아님)
- 2차: 데이터 파이프라인 설계 + 예측 로직 + LLM/RAG 실무 적용 역량을 하나의 프로젝트로 증명

---

## 2. 문제 정의

- 내한공연 관객은 공연 전 "뭘 연주할지" 궁금해하며, 커뮤니티에서 해외 투어 셋리스트를 수동으로 찾아본다.
- setlist.fm은 과거 기록만 나열할 뿐 확률·경향 분석이 없고, 영문 UI라 진입장벽이 있다.
- 곡의 배경지식(가사 의미, 라이브에서의 변주 등)은 위키·리뷰·인터뷰에 흩어져 있어 예습 비용이 크다.

## 4. 핵심 기능

### 4.1 MVP (1차 릴리즈)

| # | 기능 | 설명 |
|---|------|------|
| F1 | 밴드 조회 | 사전 등록된 밴드 5팀 검색/선택 (2026 부산국제록페스티벌 해외 라인업 기준) |
| F2 | 셋리스트 수집 배치 | setlist.fm API로 밴드별 최근 투어 셋리스트 주기 수집 (일 1회) |
| F3 | 예측 셋리스트 | 곡별 연주 확률 계산 및 확률순 정렬 표시. 셋 내 위치(오프너/본편/앙코르) 경향 함께 표시 |
| F4 | 곡 상세 (RAG) | 곡 클릭 시 배경 설명 생성 — 곡의 의미, 앨범 맥락, 라이브 특징. 출처 표기 필수 |
| F5 | 예측 근거 표시 | "최근 20회 공연 중 19회 연주" 등 예측 근거를 수치로 노출 |

### 4.2 2차 릴리즈 (MVP 이후)

- Spotify 연동 예습 플레이리스트 생성 (확률순)
- 밴드 자동 등록 (사용자 요청 기반)
- 신보 발매 가중치 등 예측 로직 고도화
- 공연 후 실제 셋리스트와 예측 비교 → 적중률 공개 (신뢰도 확보 + 콘텐츠화)

### 4.3 확장 기능 (v0.2 — 포트폴리오 강화)

데이터 수집 → 예측 → AI(RAG) → 운영 → 평가까지 포함하는 실무 수준 시스템을 목표로 아래 기능을 추가한다.
2026-07-30 코드베이스 대조 기준의 현재 상태를 함께 기록한다. 단계(P1~P3)는 `/docs/implementation-plan.md`의 구현 순서.

| # | 기능 | 내용 | 현재 상태 | 단계 |
|---|------|------|-----------|------|
| E1 | Explainable AI (예측 근거) | 곡별 확률의 계산 근거(공연별 기여 가중치, 유형 부스트 효과, 신뢰도 라벨)를 API로 노출하고 화면에 시각화 | 근거 데이터는 `prediction.evidence`(JSONB)에 전량 저장됨. API 미노출 | P1 |
| E2 | 정확도 지표 확장 | 기존 Precision@K·Recall에 **F1, Top-N Accuracy** 추가. 공연별 성적 대시보드 | Precision@K/Recall/Surprises + 자동 채점 + 아카이브 화면 구현됨 | P1 |
| E3 | 셋리스트 위치 분석 | 곡별 오프너/초반/중반/후반/앙코르 구간 비율 + 평균 위치 | avg_position, encore_ratio만 존재. 구간 비율 집계 신규 | P1 |
| E4 | 셋리스트 변화 분석 | 최근 5회/20회 등장 횟수, 등장률 추이(전·후반 비교), 페스티벌 vs 단독 등장률 차이. LLM 자연어 요약("최근 Save Me 대신 Cosmic이 자주 포함") | 최근 20회 등장·평균 위치만 응답에 존재. 수치부는 P1, LLM 요약은 P2 | P1/P2 |
| E5 | 셋리스트 통계·시각화 | 곡별 등장률, 연도별 추이, 투어별 등장률, 유형별 등장률 차트 | 집계 쿼리·차트 라이브러리 모두 없음. 신규 | P2 |
| E6 | 예상 셋리스트 자동 생성 | 확률·평균 위치·오프너/앙코르 후보·공연 유형·예상 곡 수를 반영해 실제 공연 형태(본편+앙코르 블록)의 셋리스트를 백엔드에서 생성 | 프론트 avgPosition 정렬만 존재. 백엔드 생성 신규 | P2 |
| E7 | AI 예습 코스 추천 | 30분/1시간/2시간 코스, 필수·추천·심화곡 구분, 추천 이유 제공 | 예습 체크리스트·예상 순서·듣기 링크만 존재 | P2 |
| E8 | AI 공연 어시스턴트 (RAG Chat) | 자유 질의 채팅. RAG 문서 검색 + 예측 통계 조회 두 도구를 사용해 답변, 출처 필수 | RAG 검색·생성·출처·SSE 인프라 완성. 채팅 엔드포인트 신규 | P3 |
| E9 | AI 운영 대시보드 | LLM 호출 수, 토큰, 예상 비용, 평균 응답 시간, 캐시 히트율, 임베딩 건수 | 계측 자체가 전무(호출 로그 없음). 계측 레이어부터 신규 | P3 |
| E10 | 관리자 기능 확장 | 임베딩 상태, 캐시 상태(무효화 포함), RAG 문서 관리 | 배치 실행/이력·아티스트·이벤트 관리·콘솔은 구현됨 | P3 |
| E11 | 유사 공연 분석 | 과거 공연 중 예측 대상과 가장 유사한 공연 제시(유형·국가·시기·곡 구성 겹침) | 없음. 신규 | P3 |

**요구사항 조정 (원안 대비 변경, 사유 포함)**

1. **기여도 표기는 실제 계산식을 분해해 보여준다.** 원안 예시(최근 공연 40% / 고정곡 여부 30% / …)는 현재 예측 모델과 불일치 — 모델의 신호는 최신성 감쇠와 공연 유형 부스트 2개뿐이고 "고정곡"은 화면 라벨이지 계산 요소가 아니다. 존재하지 않는 요소의 기여도를 만들어 보여주는 것은 Explainable AI 취지에 반하므로, 공연별 가중치 합산 구조를 그대로 노출한다.
2. **Accuracy(정분류율) 지표는 채택하지 않는다.** 셋리스트 예측에는 진짜 음성(TN) 클래스가 없어 정의가 성립하지 않는다. 원안의 "예측 15곡 중 13곡 적중 = 86.7%"는 기존 헤드라인 지표 Precision@K가 정확히 그 의미다. F1은 Precision@K와 Recall로 계산한다.
3. **공연 유형은 Festival / Solo 2종을 유지하고 Tour Opening / Tour Final은 보류한다.** 데이터에 투어 시작·종료 판정 근거가 없고(`tour_name` 문자열뿐), 1차 예측 대상이 페스티벌이라 효용 대비 비용이 크다. 유형 가중은 이미 `matching-show-type-boost`로 구현되어 있다.
4. **RAG Chat은 두 도구(문서 검색 + 예측 통계 조회)를 갖는 구조로 설계한다.** "Soundcheck란?" 같은 일반 질문은 문서에 근거가 없으면 원칙대로 "정보 없음" 처리하고, "신곡 나올 가능성은?" 같은 통계 질문은 RAG 문서가 아니라 예측 DB를 조회해 답한다. 출처 없는 생성 금지 원칙(§8)은 그대로 적용한다.

## 6. 시스템 구성

### 6.1 아키텍처 개요

```
[Batch] setlist.fm API ──▶ 수집/정제 ──▶ PostgreSQL
[Batch] 위키·리뷰·인터뷰 ──▶ 청킹/임베딩 ──▶ pgvector
[API]   Spring Boot ──▶ 예측 계산 / RAG 검색+생성(Spring AI)
[Web]   React SPA
```

### 6.2 기술 스택

| 영역 | 선택 | 비고 |
|------|------|------|
| Backend | Spring Boot, Spring AI | 실무 스택 연장선 |
| Batch | Spring Batch (또는 @Scheduled) | 수집 규모 작으므로 단순하게 시작 |
| DB | PostgreSQL + pgvector | RDB와 벡터 저장소 통합, 인프라 단순화 |
| Frontend | React | 마이그레이션 경험 증명 |
| LLM | API 기반(Claude/OpenAI) 우선, 로컬 LLM은 실험용 | 응답 품질 우선 |
| 배포 | 클라우드 1대 (경량) + GitHub Actions CI/CD | |

### 6.3 데이터 소스

| 소스 | 용도 | 제약 |
|------|------|------|
| setlist.fm API | 셋리스트 원천 데이터 | 비상업 용도 무료, rate limit 준수, 출처 표기 |
| MusicBrainz / Spotify API | 곡 메타데이터, 앨범아트 | Spotify는 약관 내 사용 |
| Wikipedia, 앨범 리뷰, 인터뷰 | RAG 문서 소스 | 저작권 고려 — 원문 재현이 아닌 요약·생성, 출처 링크 필수 |

## 7. 예측 로직 (v1)

- 입력: 밴드별 최근 N회(기본 20회) 공연 셋리스트
- 곡별 점수 = 등장 빈도 × 최신 가중치(최근 공연일수록 高) 
- 보조 지표: 셋 내 평균 위치, 고정곡/로테이션곡 구분
- 출력: 확률(%) + 근거 수치
- v2 후보: 신보 발매 직후 신곡 가중치, 투어 레그(대륙) 구분, 페스티벌/단독 구분

## 8. RAG 설계 (v1)

- 청킹: 곡/앨범/밴드 단위, 500~800 토큰
- 검색: pgvector 유사도 top-k(5) + 밴드/곡 메타 필터
- 생성: 검색 결과 기반 답변, 출처 미포함 내용 생성 금지 프롬프트, 출처 링크 노출
- 평가: 대표 질문 20개 셋으로 답변 품질 수동 평가 → 개선 기록 (포트폴리오 스토리)

---

## 9. 비기능 요구사항

- 예측 조회 응답 p95 < 500ms (예측은 배치 시 사전 계산, 조회는 캐시)
- RAG 응답 < 10s, 스트리밍 표시
- setlist.fm rate limit 준수 (요청 간격 제어, 실패 재시도)
- 모바일 우선 반응형 (공연장에서 보는 사용 시나리오)

## 10. 성공 지표

- 정성: 내한 공연 1건 대상 커뮤니티 공유 → 실사용 피드백 확보
- 정량: 공연 주간 MAU, 곡 상세 클릭률, (2차) 예측 적중률 70%+
- 포트폴리오: 기술 의사결정·개선 과정을 README/블로그로 문서화
